# Редактура и структурирование статей sovlium

## До правок

- Прочитай `docs-agent/reports/inventory.md`, `journeys.md` и `evidence.md` для выбранной страницы. Если пользователь попросил одну статью, собери её доказательства самостоятельно через `sovlium-journey-verify`.
- Установи **реальный** путь исходного MD/MDX, форматы frontmatter, компонентов, картинок, sitemap и sidebar. Копируй совместимый синтаксис с существующих работающих страниц. Не выдумывай поддержку специальных компонентов MDX.
- Реши, что это: `HOW-TO` («Как пригласить ученика»), `EXPLANATION` («Кому доступна доска»), `TROUBLESHOOTING` («Не работает микрофон») или `REFERENCE` (ограничения). Один материал — один основной вопрос/результат, без бессмысленного дробления.

## Содержание

- Пиши от реальной задачи и **сразу давай ответ**. Читатель — репетитор или ученик, а не разработчик.
- Пошаговые действия описывай только после `BROWSER_VERIFIED`. Используй те же слова, которые человек видит на кнопках, пунктах меню и модалках. Сложные ветки описывай отдельно, без ложного универсального сценария.
- Скажи, что пользователь увидит **после** действий: новый кабинет, ссылка, доступ ученика, статус урока и т. д. Если UI не подтвердил outcome — не утверждай его.
- Для непроверенных важных деталей используй отчёт `unverified.md`; не добавляй выдуманную инструкцию «на всякий случай». Если статья не может быть достоверно написана — оставь её без спорных утверждений и сообщи об этом.
- Отделяй функции, включённые сейчас для тестовых аккаунтов, от возможных флагов и будущего функционала. Не обещай домашние задания, автопродление, лимиты, цены и тарифы без текущего подтверждения.
- Различай возможности **преподавателя** и **ученика**, даже если речь об одной доске или одном занятии. Не обещай автоматическую доступность материалов после урока, если в интерфейсе есть настройки доступа.
- Ссылки на смежные материалы — в конце или в нужном месте как естественное продолжение, без бесконечной цепочки «читайте другую статью».

## Тон и ритм

- Бренд всегда **`sovlium`** (строчными). Человеческий русский язык, конкретные глаголы: «откройте», «нажмите», «выберите», «проверьте».
- Не используй «осуществите», «данный функционал», «интуитивно понятный интерфейс», «для максимально эффективного взаимодействия», пустые вводные и искусственный энтузиазм.
- Не делай **каждое предложение отдельным абзацем**. Группируй мысли естественно. Списки и нумерация — для действий и справки, не вместо связного текста.
- Статья не обязана подгоняться под шаблон «Введение → Преимущества → Заключение». Заголовки нужны только при реальной пользе.
- Не добавляй смайлики, маркетинговые обещания, выдуманные советы или слишком подробные пояснения очевидных кликов.
- Не раскрывай технические маршруты `xi.tutor`, internal flag names и API пользователю, если они не нужны для решения задачи.

## Навигация, миграции, иллюстрации

- По умолчанию **сохраняй существующий URL/slug** при переписывании, чтобы не ломать внешние ссылки и индексацию.
- Для объединений составь карту `old → new`, проверь реальный механизм redirects в `xi.info`, обнови внутренние ссылки и sidebar. Удалять страницу без редиректа и переноса уникального полезного содержания нельзя.
- Изображения должны соответствовать **актуальному** UI, роли, состоянию и viewport. Храни их там, где принято в проекте, с понятным именем и `alt`. Скриншоты должны быть безопасны: никаких адресов реальных пользователей, токенов, содержимого приглашения, паролей.
- Если общая инструкция сильно отличается на мобильном/десктопном виде, описывай разницу **после проверки обеих веток**; не утверждай универсальность на основе одного размера экрана.

## Definition of done (перед QA)

Статья отвечает на реальный вопрос, её критические шаги подтверждены Playwright, версия соответствует видимому приложению, связанные ссылки ведут на существующие материалы, устаревшие формулировки удалены, роль обозначена правильно, факты ограничены доказательствами. Затем обязательно передай пакет на `sovlium-docs-qa`.
