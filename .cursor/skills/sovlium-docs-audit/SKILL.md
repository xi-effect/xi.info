# Аудит базы знаний: сначала учесть всё

## 1. Найди фактические источники

- Исследуй `package.json`, workspace-конфигурацию, каталог `apps/`, пакеты, роутинг, MD/MDX, контентные коллекции, навигационные JSON/TS, публичные assets, редиректы и sitemap. Не исходи из предполагаемых путей.
- Раздели пользовательскую документацию `support.sovlium.ru`, маркетинговый сайт `sovlium.ru` и другие ресурсы `xi.info`. Исправляй именно базу знаний; ссылки на лендинг могут служить контекстом, но не заменяют инструкции.
- Составь полный реестр всех страниц из файлов **и** ссылок навигации: включи страницы без пункта меню, сиротские статьи, старые URL и возможные редиректы. Для динамических маршрутов учитывай реальную схему генерации.
- Если есть возможность, сравни файловый список с доступными ссылками опубликованного `support.sovlium.ru` через браузер.

## 2. Оцени каждую страницу

Фиксируй строку в `docs-agent/reports/inventory.md` с полями:

`Путь файла | Публичный URL/slug | Заголовок | Роль | Тип | Задача пользователя | Статус | Приоритет | Конфликты/дубли | Что делать | Основание`

Статусы: `UNREVIEWED`, `BROWSER_VERIFIED`, `CODE_ONLY`, `STALE`, `DUPLICATE`, `BROKEN`, `BLOCKED`. Это **статус доказательств**, а не обещание точности.

Для каждой страницы ответь:

- Какая конкретная задача/вопрос приводит человека сюда? Какая у него роль?
- Действительно ли страница помогает достичь результата, а не просто перечисляет функции?
- Есть ли предположительно устаревшие термины, бренды, тарифы, ограничения, UI-элементы, ссылки и скриншоты?
- Дублирует ли она другие материалы? Не нужен ли короткий раздел FAQ/ошибка вместо отдельной страницы?
- Есть ли очевидно недостающие сценарии (первый урок, ученик после занятия, доступ к доске, приглашение, проблемы со звуком)? Эти примеры — **кандидаты**, существование и поведение надо проверить.

## 3. Построй карту пользовательских путей

Пиши `docs-agent/reports/journeys.md`: для каждого пути `ID`, роль, цель, предпосылки, стартовая точка, предполагаемые переходы, результат, связанные страницы, известные пробелы, приоритет и статус проверки. Начни с кандидатного списка из `docs-agent/JOURNEYS.md`, но не считай его продуктовой спецификацией.

Приоритет:

- **P0:** действия, влияющие на первое успешное занятие, доступ ученика, материалы/доску, подключение к звонку, типичные блокеры.
- **P1:** регулярные занятия, расписание, управление учениками/материалами, счета, настройки, диагностика.
- **P2:** справочные и редкие возможности.

## 4. Подготовь план, не переписывая наугад

- Для каждой статьи выбери `KEEP / REWRITE / MERGE / SPLIT / NEW / REMOVE / REDIRECT / INVESTIGATE` и объясни почему.
- Для `MERGE/REMOVE` обязательно укажи ссылку назначения, куда перенесено **уникальное полезное содержание**, и статус редиректа. Не удаляй живые SEO-URL без обоснования.
- Выдели тексты, где есть юридические/платёжные обещания, точные тарифы/лимиты: они требуют отдельной продуктовой проверки, нельзя брать значения из памяти агента.
- Отметь границы: где интерфейс не позволяет проверить факт, а код поддерживает несколько веток/флагов.
- Не меняй исходники статей на этапе чистого аудита, если пользователь прямо не попросил сразу весь workflow.
