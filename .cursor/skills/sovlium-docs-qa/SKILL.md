# Контроль качества документации

## 1. Содержательные проверки

Для **каждой** изменённой страницы:

- Кто читатель (репетитор/ученик) и какой результат он получит? Ответ заметен с начала статьи?
- Сопоставь каждую критическую инструкцию с `docs-agent/reports/evidence.md`: точное название UI-элемента, видимая ветка, результат, роль и дата подтверждения. Если доказательств нет — запроси повторный browser check или убери утверждение.
- Сверь условия прав доступа, статусы урока, поведение приглашений, доступ после завершения урока, тарифы/лимиты и feature flags с фактическим UI; код из `../xi.tutor` — вторичная опора, а не доказательство доступности функции.
- Убедись, что статья не склеила несовместимые роли/потоки, не придумала кнопку или доступ по умолчанию.
- Удали повторы, воду, канцелярит, рубленый ритм «предложение = абзац», искусственные подводки и маркетинговые фразы. Проверь, что бренд пишется `sovlium`.

## 2. Технические проверки в xi.info

1. Определи **фактический** пакет support/docs и существующие npm scripts, тип роутера и сборку. Нельзя автоматически подставлять выдуманное имя workspace.
2. Запусти доступные целевые проверки: MDX parse/typecheck/lint/build или `npm run build --workspace=<реально найденный workspace>` в соответствии с проектом. У корня `xi.info` используются npm workspaces; опирайся на реальный `package.json`.
3. Проверь внутренние ссылки и якоря, sidebar/navigation, ссылки на assets, публичные старые маршруты и редиректы. Если проверка ссылок автоматизирована в проекте, используй её; иначе пройди важные переходы через Playwright.
4. Если были правки скриншотов: актуальный интерфейс, читаемость, отсутствие полей паролей/персональных данных/ссылок-приглашений. Скриншот должен подтверждать именно тот шаг, возле которого расположен.
5. Просмотри `git diff` и `git status`. Убедись, что не изменены `xi.tutor`, продуктовые функции, unrelated files, локальные env, browser profiles, browser storage state и случайные артефакты Playwright.
6. Проверяй, что новые статьи видны в реальной навигации/поиске согласно архитектуре проекта, а не просто добавлены файлом в каталог.

## 3. Browser re-check после правок

- Если документация запускается локально, открой изменённые страницы и проверь рендер, картинки, навигацию.
- Выборочно возьми **хотя бы один** критический шаг каждой статьи и повторно проверь его в `app.sovlium.ru`. Для спорных статей — весь сценарий.
- Не называй локальный рендер проверкой продуктового пользовательского пути: проверяются **два разных сайта**.

## 4. Итоговый отчёт

Обнови `docs-agent/reports/status.md` с фактическими результатами:

```md
## Проверка пакета YYYY-MM-DD

- Страницы изменены: ...
- Путь/роль, реально пройденные Playwright: ...
- Доказательства: ...
- Сборка/линтер: PASS / FAIL / NOT RUN (+ почему)
- Ссылки и редиректы: PASS / FAIL / PARTIAL
- Непроверенные утверждения и блокеры: ...
- Следующий пакет: ...
```

Никогда не объявляй PASS проверке, которая не запускалась. Не скрывай ошибки сборки под фразой «проверено». Исправь обнаруженные ошибки или явно передай ограничение.
