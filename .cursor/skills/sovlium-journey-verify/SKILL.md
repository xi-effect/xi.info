# Проверка пользовательских путей через Playwright

## Подготовка и вход под двумя ролями

1. Пользуйся **реальными инструментами Playwright MCP** (`browser_navigate`, `browser_snapshot`, `browser_click`, `browser_type`/`browser_fill_form`, `browser_take_screenshot` и т. п.). Узнай фактические имена инструментов, доступных в текущей сессии. Недостаточно «посмотреть код» или визуально изучить support: необходимо выполнить шаги через браузер.
2. Основные адреса: `https://app.sovlium.ru/` и `https://support.sovlium.ru/`. Если задан безопасный тестовый стенд, используй его вместо production.
3. Предпочтительно два **разных MCP-сервера** из `.cursor/examples/mcp.playwright.json`: `playwright_tutor` и `playwright_student`. Каждый сервер запущен с `--isolated`, поэтому хранит собственные cookies и может одновременно работать со своей ролью. **Не используй две вкладки одного контекста** для двух аккаунтов: у них общие cookies.
4. Конфигурация передаёт Playwright MCP файл секретов `docs-agent/.env.docs.local` через `--secrets`. **Никогда не читай и не печатай содержимое файла.** На странице входа сначала проверь snapshot, затем введи в email/пароль исключительно строки-заместители:
   - в `playwright_tutor`: `SECRET_DOCS_TUTOR_EMAIL` и `SECRET_DOCS_TUTOR_PASSWORD`;
   - в `playwright_student`: `SECRET_DOCS_STUDENT_EMAIL` и `SECRET_DOCS_STUDENT_PASSWORD`.
     Playwright MCP заменит эти placeholder-строки значениями из локального файла **на своей стороне**. Не используй пароли из чата в коде, tool arguments, отчётах или конфиге. Если placeholders не подставились, останови автоматический вход, отметь блокер и попроси один раз авторизовать каждый профиль вручную; не перебирай учётные данные.
5. После входа подтвердить **видимую роль** каждого аккаунта (доступные меню, персональное пространство), а не просто отсутствие формы входа. Не предполагай, что авторизация прошла только потому, что URL изменился. У каждого прогона должны быть явно зафиксированы роль, состояние и время.
6. В production — только минимальные обратимые действия с подготовленными тестовыми аккаунтами. Не инициируй платежи, рассылки, массовые операции, удаление чужих данных; не отправляй приглашения посторонним. Убедись, что создаваемые сущности действительно тестовые. При риске необратимого действия остановись и пометь шаг `BLOCKED`.

## Выполнение пути

Для **каждого** `journey ID`:

1. Опиши цель простым языком от роли («репетитор хочет пригласить ученика на первое занятие»), стартовое состояние, prerequisites и ожидаемый критерий успеха. Обозначь, какие сущности временно создаются.
2. Открой UI под правильной ролью. Сними исходный **accessibility snapshot** и URL; после каждого значимого перехода проверяй состояние, актуальный текст кнопки, поля, модалки, ошибку, конечный экран.
3. Пройди последовательность **кликами и вводом в реальном браузере**. Не переходи напрямую по предположительному внутреннему URL, если задача — проверить путь через интерфейс. При ошибке опиши видимое сообщение, что его вызвало и возможно ли повторить.
4. Для межролевых путей проверь сначала действия репетитора, затем **именно учеником** при принятии приглашения, доступе к материалам и участии в занятии. Убедиcь, что речь об этих двух тестовых аккаунтах.
5. Проверяй ветки, влияющие на текст статьи: уже созданный/новый кабинет, зарегистрированный/новый ученик, разрешения доски, повторяющееся занятие, роль, условие подписки, feature flag, desktop/mobile — только когда релевантны и доступны.
6. Для непонятных условий читай `../xi.tutor`: ищи маршруты, тексты локализации, permissions, feature flags и state-ветки. Сохраняй только путь к файлу и краткий смысл; **наличие кода не заменяет браузерную проверку**. Изменять `xi.tutor` запрещено.
7. Проводя проверку, по возможности открой текущую статью `support.sovlium.ru` и сравни **каждый процедурный шаг** с реально видимым UI. Не переноси устаревшие шаги в новую версию.
8. Скриншоты делай только там, где изображение существенно проясняет действие; не снимай поля паролей, секреты приглашений, личные данные. Прежде чем включить снимок в документацию, проверь безопасную обрезку/маскирование и принятый в `xi.info` формат хранения.
9. Удаляй **только созданные этим прогоном** временные сущности, если очистка безопасна и предусмотрена. Не удаляй ничего неизвестного и не создавай бесконечное количество мусорных кабинетов/занятий.

## Фиксация доказательств

Добавь в `docs-agent/reports/evidence.md` запись по шаблону:

```md
## JOURNEY-ID — краткое имя

- Дата проверки:
- Роль и состояние аккаунта:
- Среда, размер viewport и необходимые feature flags:
- Цель / критерий успеха:
- Реальный путь в UI (последовательность фактических названий):
- Конечное состояние и URL:
- Что показал Playwright (успех / частично / ошибка):
- Сверка с xi.tutor (пути файлов, только если действительно читались):
- Затронутые страницы документации:
- Безопасные изображения (если есть):
- Неуверенности, альтернативные ветки, причины блокировки:
- Результат: BROWSER_VERIFIED / PARTIAL / CODE_ONLY / BLOCKED
```

Не публикуй публично эти отчёты с персональными данными и секретными ссылками. Храни время, способ проверки и **границы проверенного**, чтобы следующая итерация могла отличить актуальный факт от старой гипотезы.

## Если Playwright недоступен

Не подменяй его чтением сайта через curl или кодом. Проверь, что MCP настроен, отметь `BLOCKED`, дай точную инструкцию подключения из `README.md`, и продолжи допустимый кодовый аудит, ясно маркируя его `CODE_ONLY`. Вручную написанные «пройденные шаги» запрещены.
